Every component is tested at three layers. All of them read the same source of truth: the example files in
`src/components/<name>/examples/*.vue` that also power the live previews on this site.

| Layer | Tool | Runs in | What it proves | Command |
| :--- | :--- | :--- | :--- | :--- |
| Unit | Vitest + `@vue/test-utils` in happy-dom | Node, no browser | Variants, classes, emitted events, ARIA attributes, pure logic | `bun run test:unit` |
| Browser | Vitest browser mode + Playwright Chromium + `axe-core` | Real Chromium | Every example renders with zero axe violations in both themes; keyboard, focus and v-model behavior | `bun run test:browser` |
| Visual | Playwright screenshots on the built docs site | Playwright Docker image | Every example looks the same as its approved baseline, in both themes at 1280 and 360 px | `bun run test:visual` |

`bun run test` runs unit and browser tests together and is part of `bun run check`. The visual layer is a separate CI job
because its baselines are only valid inside one pinned operating system image.

## Unit tests

Files named `src/components/<name>/<Name>.test.ts`. They mount the component with `@vue/test-utils` and assert on the DOM:
rendered element, `data-*` slots, variant classes, emitted events, `aria-*` attributes. They are fast and have no
styling, so keep behavior that needs real layout, focus management or computed styles in the browser layer.

## Browser tests

Files in `tests/browser/`. The Vitest `browser` project runs them in headless Chromium with the real Tailwind build and both
theme files loaded, so computed colors, focus rings and layout are real.

- **Accessibility sweep** (`examples.test.ts`): discovers every `src/components/*/examples/*.vue` with `import.meta.glob`,
  mounts it, switches `data-theme` between `elf` and `nova`, and runs `axe-core` over the document. The expectation is an
  empty violation list. Examples whose root contains a dialog trigger are opened first so the portalled content is audited
  too. Page-level rules (landmarks, one `h1`) are disabled because an example is a fragment, not a page. A new example is
  covered automatically; it only has to exist.
- **Interaction tests** (`interactions.test.ts`): real pointer and keyboard input through `userEvent`. Dialog focus moves in,
  is trapped, returns to the trigger on close, and the page behind is hidden from assistive technology; Tabs respond to the
  arrow keys, Home, End and manual activation; Button `as-child` keeps a single link element; Input `v-model` stays in sync.
  These run in both themes.

```bash
bunx playwright install chromium   # once
bun run test:browser               # all browser tests
bunx vitest run --project browser -t Dialog   # a subset
```

Failure screenshots are written to `.vitest/attachments/` (git-ignored).

## Visual regression

The docs site contains a hidden harness route per example: `/__examples/<component>/<example>?theme=elf|nova`. It
renders the example alone on the theme background, without site chrome, is `noindex`, disallowed in `robots.txt` and absent
from the sitemap and the search index. Animations and transitions are disabled, the caret is hidden and the page flags
`<html data-ready="true">` once fonts have loaded and the example is mounted.

`tests/visual/examples.spec.ts` enumerates the examples, then for each theme and each viewport (1280 and 360 px) opens the
route, opens the dialog for overlay examples, checks that nothing overflows horizontally and compares a screenshot with
`tests/visual/__screenshots__/<component>/<example>-<theme>-<width>.png`. Comparison is exact.

::callout{type="warning" title="Baselines come from Docker only"}
Fonts and the rasterizer differ between operating systems, so a PNG made on your laptop never matches CI. Baselines are
generated only by the **Visual baselines** workflow, in `mcr.microsoft.com/playwright:v1.64.0-noble`, the same image the
**Visual regression** job uses. Do not commit baselines you generated locally.
::

You can still run the visual suite locally to debug the harness (the layout checks work everywhere; screenshot comparisons
will differ from CI):

```bash
bun run docs:build                  # the tests serve apps/docs/.output/public under /elfUI/
VISUAL_PORT=4390 bun run test:visual
```

## Reviewing and updating visual baselines

When a change intentionally alters how a component looks, the **Visual regression** job fails on the pull request and uploads
the report (`visual-report` artifact: expected, actual and diff images). Then:

1. Open a pull request with your change (baselines are never updated on `main`).
2. In GitHub, go to **Actions - Visual baselines - Run workflow** and choose your branch. The workflow builds the docs site in the
   Playwright image, regenerates the screenshots and commits only the PNGs that changed to your branch as
   `test(visual): update baselines`.
3. Review the PNG diff in the **Files changed** tab of the pull request. GitHub shows image diffs (swipe, onion skin, 2-up).
   Every changed image must be explained by your change; unexpected differences are bugs, not noise.
4. A push made by the workflow does not start other workflows. Push an empty commit (`git commit --allow-empty`) or re-run the
   **Visual regression** job so the required checks run against the new baselines.
5. Merge when checks are green and a reviewer has approved the image changes.

A new example has no baseline yet, so the job fails with "A snapshot doesn't exist"; run the workflow once to create it.
Deleting an example leaves orphan PNGs behind: delete them in the same pull request.

## What runs where

| Check | Locally | In CI |
| :--- | :--- | :--- |
| Unit and browser tests (`bun run test`) | Yes | **Check** job (inside `bun run check`) |
| Pre-push hook | typecheck, lint, unit tests | - |
| Visual regression (`bun run test:visual`) | Debug only | **Visual regression** job (Playwright image) |
| Baseline regeneration | Never | **Visual baselines** workflow |

## When you add a component

A component is done when it has unit tests, examples that pass the axe sweep in both themes (automatic), interaction tests for
any behavior beyond rendering, and committed baselines for its examples. See [Contributing](/docs/resources/contributing).
