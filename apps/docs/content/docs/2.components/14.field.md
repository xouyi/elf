## Usage

```vue
<ElfField label="Email" description="We only use it for match reminders." :error="errors.email" required>
  <ElfFieldControl>
    <ElfInput v-model="form.email" type="email" />
  </ElfFieldControl>
</ElfField>
```

Reka UI has no field primitive that fits ElfUI's layout, so `ElfField` is composed from [Label](/docs/components/label) and native elements. It works with [Input](/docs/components/input), [Textarea](/docs/components/textarea) and any native control or component that passes attributes to its root element.

## The wiring pattern

`ElfField` generates an id and shares it with its parts through provide and inject. `ElfFieldControl` wraps **one** control and merges the wiring attributes onto it (it renders no element of its own):

| Attribute on the control | Set when |
| :-- | :-- |
| `id` | Always. The label points at it with `for`. |
| `aria-describedby` | A description and/or an error is rendered. Lists `<id>-description` then `<id>-error`. |
| `aria-invalid="true"` | The field has an `error` or `invalid` is set. |
| `aria-required="true"` | `required` is set. |
| `disabled` | `disabled` is set. |

Attributes you put on the control yourself are kept, except the ones in the table: the field wins, so that the label and the description always match the control. To add your own description, render an `ElfFieldDescription` inside the field.

Use the parts directly for custom layouts. Each part reads the field context, so ids and the live error region stay in sync:

```vue
<ElfField id="slug">
  <ElfFieldLabel>Slug</ElfFieldLabel>
  <ElfFieldControl><ElfInput /></ElfFieldControl>
  <ElfFieldDescription>Lowercase letters and dashes.</ElfFieldDescription>
  <ElfFieldError v-if="slugTaken">That slug is taken.</ElfFieldError>
</ElfField>
```

A custom control component can read the same data with `useFieldContext()` (exported from the package).

`required` adds a visual asterisk (hidden from assistive technology) and `aria-required="true"` on the control, so the requirement is announced once. The field does not set the native `required` attribute, so the browser shows no validation bubbles of its own.

## Accessibility

- The label is a native `<label for>` pointing at the control, which gives it its accessible name and a larger click target.
- The description and error are referenced with `aria-describedby`, so screen readers read them after the label when the control receives focus.
- The error has `role="alert"`: when it appears after the user acts, it is announced immediately. Do not render an error on first load, or every field would announce at once.
- `aria-invalid="true"` marks the control and turns its border destructive; the message states the problem and how to fix it, so color is never the only cue.
- Text color for errors is derived from the `destructive` token and mixed with the foreground to keep 4.5:1 contrast on the dark surfaces of both themes.

| Key | Action |
| :-- | :-- |
| <kbd>Tab</kbd> | Moves focus to the control. The label, description and error are not focusable. |
| Click on the label | Focuses the control. |

## Do and don't

| Do | Don't |
| :-- | :-- |
| Give every control a label through `label` or `ElfFieldLabel`. | Use a placeholder as the label. |
| Write errors that say how to fix the problem. | Show only "Invalid value". |
| Wrap exactly one control in `ElfFieldControl`. | Wrap several controls; use a fieldset for groups. |
| Show errors after blur or submit. | Show errors while the user is still typing the first character. |
